# napier: notes for agents

- Scope: facts about how music hardware works (manuals, firmware changelogs, community docs, pinned firmware source code, and the owner's own rig notes) and a ledger of checked claims. It doesn't hold samples or lessons.
- Data layout: public data ships in the repo (`sources.yaml`, `facts/`, `specs/`, `catalog/modules.yaml`, `examples/`). The owner's own rig lives in the private overlay `local/` (gitignored, its own repo): `local/sources.yaml`, `local/facts/`, `local/racks/`, `local/notes/`, `local/napier.toml`. Without an overlay the rack commands read `examples/racks` and refuse to write. Never move overlay data into the public tree, and never commit names, rack URLs or rig notes to it. `src/napier/paths.py` documents every override.
- Look things up with the CLI (`napier`) or the `napier` MCP tools. Prefer `grep` and `read` for exact wording, button combos and whole sections; use `search` for open questions. Cite what the tool prints: title, version, printed page.
- When the user confirms something on hardware, record it: `napier facts add <device> "<claim>" --status hardware --notes "..."`, or `napier facts verify <id> --hardware --note "..."` for one of their open questions. When a claim turns out wrong, `--refute` it rather than deleting it. With an overlay, new facts go to `local/facts/`. A device can have facts in both `facts/` and `local/facts/`, and napier reads both.
- The public ledger is testable: every fact in `facts/` has a source and anchors (and printed pages for a PDF), with status manual, changelog, community, code or refuted. Hardware checks, open questions and forum paraphrases stay in the overlay. `tests/test_data.py` checks this, and `set_status` refuses to make a public fact hardware or unverified.
- New sources are added with `napier source add`. Pin manuals (sha256); leave changelogs and community docs unpinned. Run `napier source offset <id>` for PDFs and check the result. `source add` only writes a detected offset when at least 3 pages carry a number and most agree; otherwise it writes 0 and warns, and `source offset` marks the guess unsure. Footers like `pg 48` count. For product pages and shop pages, crop to the changelog part with `--start-at`/`--stop-at` regexes so price or stock churn doesn't read as an update. With an overlay (`napier init` creates one), `source add` writes to `local/sources.yaml`; `--public` adds to the public list for a pull request. Private sources (the owner's notes, private documents) always go in the overlay.
- Polite fetching, always: napier is not a scraper. `source add` checks robots.txt and refuses disallowed URLs (don't reach for `--ignore-robots`); it sends an honest user agent; `source check` fetches each source once per run (weekly), spaces requests to a host by 2 s (longer if robots.txt sets a Crawl-delay), backs off on 429/503, follows redirects only to public addresses robots.txt allows, never crawls links, never logs in. When robots.txt disallows a document, the user downloads it in a browser and runs `napier fetch --source ID --from FILE`. Forum threads (format `discourse`, via the topic's `/raw` pages), pinned code and Google Drive downloads are `check: false` snapshots: fetched once, never polled. A shared doc its authors keep updating (like a community tips doc) is re-checked like a changelog. Don't add forum crawls, search-result scrapes, or anything behind a login.
- Kinds: `manual`, `changelog`, `community` (forum snapshots: opinions and workarounds, cite as such), `code` (source pinned to one commit, for details the manuals skip; fact status `code`), `note` (the owner's own files, usually in `local/notes/`; facts from hand-written rig notes are status `hardware`).
- Rack: `napier rack sync` reads the rack through the rack source named in `racks/devices.yaml` (`rack_source`; built in: `file`, which reads `layout.yaml`; plug-ins register under the `napier.rack_sources` entry-point group, see `src/napier/rack_sources.py` and `napier rack sources`). It writes the `racks/<rack>.yaml` snapshot and the generated `notes/rack.md`, and reports modules added, removed, or unmapped. `--set KEY=VALUE` passes one-off settings to the source. An unmapped module is the cue to add its manual and map its slug in `catalog/modules.yaml` (or the rack's own `modules:`). Don't hand-edit generated files. `devices.yaml` also holds `geometry` (how the rack splits into cases), `off_rack` (owned modules not in the rack) and `wishlist` (modules the owner does NOT own). A `planning` rack, when the source supports one, adds every module on it the owner doesn't own to the wishlist. Wishlist entries come back with `owned: false` and stay out of `rack export` unless `--wishlist` is passed. Never describe a wishlist module as owned.
- Specs: `specs/<module>.yaml` holds manual-cited power (mA per rail, with page and an exact anchor) and the module's front-panel jacks (name, dir, type, page). `napier specs check` verifies every anchor and jack name on its cited page; `napier rack check` compares manual power with the rack source's figures. Add a spec for every new module, only from the manual text, never from memory or a rack-planning site; note gaps in `notes`.
- Rack usage: `racks/usage.yaml` is hand-written with the owner and never generated. Per module slug it records the module's `job`, `status` (anchor = never fire, keep, candidate = could go, leaving, planned, considered), `pairs_with`, `keep_near`, `distance_ok`, `notes`, and `open` questions; `cases` records each case's supply (`power` as text, `limits` in mA per rail), `mode` and row-by-row `layout` intent; `rules` holds rack-wide placement rules. Only write what the owner said: anything unconfirmed goes in `open`, and answering one means asking. `napier rack usage` checks it and regenerates `notes/rack-usage.md`. Treat it as working defaults that can be challenged (its `stance` says so): start from it, and challenge any default when there's a clear hypothesis for an alternative, naming what changes and what should play or patch better. Every challenge and the owner's response is logged in `racks/challenges.yaml`; read it before proposing one, and don't re-raise a rejected challenge without new evidence.
- Scenarios: `racks/scenarios/<id>.yaml` are what-if layouts (hand-written): start from the actual rack, `remove` slugs, `place` slugs at full position lists ("row N, hp N"). `napier rack scenarios` resolves them and reports problems (overlaps, case seams, 1U/3U rows), power per case against the supplies, pairs farther than 20 cm or across cases (`distance_ok` marks accepted ones), and split free space. Write a scenario whenever a layout is worked out in conversation, so it isn't lost in chat.
- Rack viewer: `napier rack view [--out PATH] [--fragment] [--open]` draws the actual rack and every scenario as one self-contained page. Keep `rack export`'s JSON shape stable (add fields, don't rename).
- A fact with `q` + `anchors` is a search test, and anchors always come with a `q`. Anchors must appear verbatim (alphanumerics, case-insensitive) in one chunk on the fact's printed `pages`. Run `napier eval` after changing sources, chunking or models; it fails below hit@3 90%.
- Style for anything user-facing: casual but professional, direct, no em dashes.
- Tests: `pytest` (no models needed), `ruff check src tests`, `mypy`. Every command shown in a code block in README.md, CONTRIBUTING.md or docs/ must parse (`tests/test_readme.py`).
- Anchors are short quotations: at most 25 words each (docs/data-policy.md). Claims are in the contributor's own words.
- MCP tools take `device_id` for the device filter. The Claude desktop bridge drops any tool argument named `device` (it uses that name to route calls to a computer), so a `device` filter would silently do nothing.
- Keeping sources current: `napier source check` re-downloads every source (except `check: false` snapshots and local files) and reports same/changed/gone (changed files wait in ~/.napier/pending). `napier source apply <id> [--url NEW] [--version V]` swaps one in (file, pin, fetched date, page offset), then `napier ingest --source <id>` and `napier facts recheck` (lists facts whose anchor vanished or moved page; `--fix-pages` fixes moves). A vanished anchor means the claim needs re-checking against the new text: re-anchor it if still true, `--refute` it if not, never just delete it. `check` can't see a newer manual published under a new filename; look at the maker's product page for that.
- Unattended pass: `napier refresh [--merge]` runs check, rack sync, apply, ingest, recheck, lets a local Ollama model (NAPIER_LOCAL_MODEL) reword eval questions only for facts whose source changed (judged by search, 3 tries), runs the full eval and tests, and opens a PR (with --merge, squash-merged automatically once CI passes, if the gate passed locally). What it cannot settle is listed in ~/.napier/reports/latest.md. Changes to the overlay are committed and pushed to its own repo; public changes go through a PR, and only after the overlay's own tests (`local/tests`) pass, so a private guard there can stop a push.

Notes about your own setup can live in `local/CLAUDE.md` (gitignored, in your overlay); this imports them when the file exists: @local/CLAUDE.md
